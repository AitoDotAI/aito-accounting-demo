## Aito quirks discovered

- **`$or` on a predict target nulls the target field** on every hit after
  the first, with a 200. The linked-key form (`invoice_id.invoice_id`) does
  not. A client reading the predicted field silently loses every candidate
  but one. `td-20260916101358316761`.
- **`_match` is byte-identical to `_predict` on a linked column** — same
  `$p` to six decimals. The cheatsheet implied it was a second capability.
- **A linked path in a `where` is an exact, case-sensitive filter even
  inside `_predict`.** `invoice_id.vendor` with a different case, a partial
  name, or an unstored value each return 0 hits. So it cannot carry fuzzy
  vendor evidence — which rules it out for the payer-entity work.
- **2.9.0 makes a bare value on a `Text` column exact in a filter.**
  `corporate_entities.name` bare `"BASF Oy"` → 1 (was 2), `"Kardex"` → 0.
- `nameBoost` was **not** removed in 2.8.4, contrary to an earlier note
  here. It is live on 2.9.0. When the candidate domain was wrong it decided
  matches at 23.3× over evidence that was uniformly ≤ 1.0
  (`td-20260916095541763810`); once the domain is the ledger it flips to
  ~0.2 and merely dampens.

## Surprising

- **A confident wrong diagnosis survived a test that looked decisive.**
  Perturbing a matched payment's reference digits collapses the match,
  which reads as the model retrieving the payment's own row. It does not
  follow — a reference no invoice carries collapses it under the innocent
  explanation too. The discriminating test uses a reference that exists on
  an invoice but is quoted by no transaction. Written up in ADR 0020
  rather than deleted, because the wrong version was the plausible one.
- **`./do check` had been red independently of any change** — `aito-check`
  ran through the v1 client, which cannot open the tables post-cutover.
  Nobody noticed because the gate was not being run.
- The match book *demonstrated the unscoped query shape*, so the reference
  documentation was teaching the bug it failed to catch.
