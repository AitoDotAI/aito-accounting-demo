# Session 2026-06-23

## Pattern Rule Discovery — `$patterns` conjunction mining (branch `feature/pattern-rule-discovery`)

Replaced the single-field rule miner (ADR 0006) with Aito's new
`$patterns` operator, which mines multi-field AND-conjunction rules
(`vendor X AND category Y → GL Z`) server-side in one `_relate` per GL
code. Wrote ADR 0014, added `AitoClient.relate_patterns()`, rewrote
`rulemining_service.py` around `$and` conjunctions, retired the
`/api/rules/sub_patterns` chaining endpoint, reworked the Rule Mining
page to render conjunctions, and refreshed cheatsheet / README /
demo-script / use-case docs. Not yet merged.

## Aito quirks discovered (all verified live, the hard way)

- **Stats roles invert under `$patterns`.** With the GL target pinned in
  `where`, the conjunction is the `related` side, so precision is
  `fOnCondition / f` and coverage is `fOnCondition / fCondition` — the
  reverse of single-field `_relate`. Getting it backwards silently
  produces wrong support ratios.
- **Multi-tenancy must use a nested `from`, not a `where` filter.**
  Putting `customer_id` in the `where` alongside the GL target makes the
  linked `customer_id` the condition and mines the *global* table
  (`n=128000` vs the tenant's `16000`). The booktest caught this. Fix:
  `from: {from: invoices, where: {customer_id}}`, `where: {gl_code}`.
- **`$related`'s default `infoGain` surfaces anti-correlations.** Some
  candidates match many rows but never the target (`fOnCondition=0`).
  Gate `MIN_SUPPORT` on `fOnCondition`, not `f`, to drop them.
- `_relate` *does* accept `select` (cheatsheet previously claimed it
  didn't — corrected).
