# Session 2026-06-24

Continuation of the `$patterns` rule-discovery work (branch
`feature/pattern-rule-discovery`, ADR 0014). Three issues surfaced and
were fixed; the feature is materially stronger as a result.

## 1. Stale caches hid the new rules

The Rule Mining page showed old single-field rules. Cause: reads go L1
(in-process) → Aito `precompute_entries` (L2) → local JSON (L3). I'd only
rewritten the L3 files, which L2 shadows. Fix: push regenerated rules
through `precompute_store.put` (L2) and bounce the server to clear L1.
The served frontend export was also stale — rebuilt it.

## 2. Support showed 100% but the drill-down had exceptions

`$patterns`' `fs` are **smoothed model estimates, not exact counts** —
the raw response carried `f = 836.35546875` (fractional) and rounded
rules to deterministic. So "836/836 = 100%" while the exact-search
drill-down listed a different-GL invoice. Fix: use `$patterns` only to
*discover* conjunctions; recompute support/coverage/lift with exact
`_search` counts (`discover_conjunctions` + `build_candidate`). The
drill-down now also fetches all exceptions explicitly and returns exact
totals. Headline and drill-down agree (815/831 = 98.1%).

## 3. Rules mixed inputs and outputs (leakage) — the big one

Candidate fields included `approver`/`cost_centre`, which are *outputs*
assigned during coding — not known when a rule would fire. In the
fixtures `vendor → category → gl_code`, and `approver` is a sibling
output of `category`, so it was a leaky proxy. Resolution (Antti's call:
inputs-only + enrich data + multi-target):

- **Inputs only:** `CANDIDATE_FIELDS = [vendor, category, vendor_country,
  amount_band]`.
- **`amount_band`:** new derived categorical field (small/medium/large).
  `$patterns` can't mine a numeric `amount` (verified — it's ignored).
- **Capitalization split:** generator now books large IT/software/
  maintenance purchases to a new `1600` capital GL — the one place
  `gl_code` depends on more than vendor/category.
- **Multi-target:** mine rules for `gl_code` **and** `approver`, each
  from inputs only. The approver's existing amount escalation makes it
  the natural multi-field showcase.

Live result (CUST-0000): 26 rules, 20 strong, across both targets —
capitalization `vendor="Bronex Software Oy" AND amount_band="large" →
1600` (144/145) and escalation `vendor="Avarn Security Oy" AND
amount_band="large" → Markku Heikkinen` (925/925).

## Aito quirks (verified live)

- `$patterns` `fs` are estimates (fractional, smoothed) — never display
  them as exact support; recompute with `_search`.
- `$patterns` ignores numeric fields — derive a categorical band.
- (from 23rd) stats role inversion; multi-tenancy needs a nested `from`;
  `infoGain` surfaces anti-correlations (filter `lift > 1`).

## Data reload

Schema gained `amount_band`, so `invoices` (+ its link dependents
`bank_transactions`, `overrides`) were dropped and reloaded. The
sequential loader timed out at 20 min mid-upload (left tables partial);
a **parallel** batch upload (6 workers, 2k batches) restored all three
in ~4 min. Fixtures regenerated with `--medium` (128k invoices, RNG
stream unchanged so the diff is just `amount_band` + capex GLs).

## 4. Rule diagnostics (ADR 0015)

Added a diagnostic to the drill-down: `_relate` over the rule's matched
population, scoring each *remaining* input by lift toward the output, to
explain the exceptions. lift < 1 marks exceptions, lift > 1 marks
agreements; when the exceptions concentrate on one feature value it
proposes a refinement. Verified: `K. Itäluoma AND maintenance → 1600`
→ exceptions are `amount_band=medium` (0/26) → "add `amount_band=large`";
`Dottoressa AND consulting → 5400` → all lifts ≈ 1 → "exceptions look
random." New `AitoClient.relate_features`, `diagnose_rule` /
`interpret_diagnosis`, `GET /api/rules/diagnose`. The drill-down modal is
now two-column (invoices + diagnostic) and invoice rows expand to full
detail on click.

## 5. Diagnostic perf — progressive load + `$on`

The diagnostic `_relate` was slow (~7 s) and blocked the whole drill-down.
Two fixes:
- **Progressive load:** the modal fetches invoices and the diagnostic
  independently; invoices render immediately (~0.5 s) and the right panel
  fills in with a spinner when the relate returns.
- **`$on` not nested-`from`:** the diagnostic relate now scopes via the
  `$on` proposition on the flat table instead of a nested-`from`
  subquery — **138 ms vs 7 s**, ~50× faster, identical result. Aito hits
  the index directly. (Recorded in the cheatsheet; `$patterns` still
  needs nested-`from`.)
